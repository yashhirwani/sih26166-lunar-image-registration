# Demo Cases

Frozen, real pipeline outputs for the PS166 demo, generated from the data
bundled in `data/test_set/` and `data/reference/`. Regenerate with
`python generate_demo_cases.py` from the project root (script kept in the
repo root next to `app.py`), or see `scripts/run_benchmark.py` for the
tabular benchmark sweep (`benchmark_results.md` / `.json` in this folder).

**Overlap confirmation status is load-bearing here** — see
`data/test_set/README.md`. Only Case 1 has a confirmed genuine ground
overlap. The other two cases exist to show real pipeline behavior
(including honest low-confidence/failure reporting), not to claim
verified accuracy.

## Case 1 — `case1_easy_ohrc_ohrc/` — CONFIRMED overlap

Two browse-render variants of the **same** OHRC acquisition
(`20260102T1224107393`). Near-identical illumination/geometry — this is
the pipeline's sanity-check pair and the only one with a verified overlap.

Result: method **SIFT**, confidence **HIGH**, 317 inliers (100% ratio,
100% spatial coverage), fit RMSE 0.0194px, **held-out RMSE 0.0195px**
(computed on 79 inliers never used to fit the transform) — sub-pixel
accuracy achieved and independently verified.

Contains: `registered_image.png`, `checkerboard.png`, `side_by_side.png`,
`difference_image.png`, `match_visualization.png`, `spatial_heatmap.png`,
`metrics_report.txt`, `result.json`.

## Case 2 — `case2_medium_candidate_UNCONFIRMED/` — UNCONFIRMED overlap

Two consecutive-frame OHRC crops from the same orbit pass
(`20210405T0047199117` vs `20210405T0047199239`). **No footprint/lat-lon
metadata was available to confirm these two crops actually share
terrain** (see `data/test_set/README.md`, Tier 2). The pipeline found a
strong geometric fit (AKAZE, 320 inliers, HIGH confidence) — which shows
the matcher works on harder illumination/viewpoint variation, but **this
is not proof of registration accuracy** without a confirmed ground truth
to check against. Presented as a pipeline-behavior demo only.

## Case 3 — `case3_cross_sensor_PLUMBING_DEMO/` — NOT a verified pair

Attempts `register_cross_source()` against the bundled
`data/reference/lro_south_pole.tif` GeoTIFF using an OHRC browse PNG that
has **no accompanying XML metadata** in this repo, so its true lunar
location is unknown to the pipeline. The result is an **honest, expected
failure**:

```
Source and reference footprints do not overlap. Source bbox: lat [0.0000,
0.0000] lon [0.0000, 0.0000]. Reference bbox: lat [-84.1649, -71.2304]
lon [-15.9641, 89.9410].
```

This demonstrates the graceful-failure path (`result['success'] = False`
with a clear `failure_reason`, no crash) rather than registration
accuracy. To get a genuine cross-sensor demo, `register_cross_source()`
needs an OHRC source with real corner lat/lon (from
`ohrc_loader.parse_ohrc_xml()` on an actual `.zip`/XML bundle, not a bare
browse PNG) whose footprint is confirmed to fall inside the reference
tile's coverage. Cross-sensor matching (OHRC vs LRO NAC/WAC, and IIRS
hyperspectral) remains **experimental and not yet benchmark-validated**
on confirmed overlapping data — see the README's Known Limitations.
